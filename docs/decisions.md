# decisions.md — 決定台帳（追記専用）

既存行の編集・削除は禁止。覆す場合は新しい D 番号で「D-00x を覆す」と明記する。

## D-001 技術構成は仕様書どおり Vite + TypeScript + Three.js
2026-09-01。STAGING リポジトリは静的プロトタイプ置き場だが、仕様書の CLAUDE.md が
「勝手にフレームワークを変更しない」と明示しているため従った。ビルド成果物
(`dist/`) はコミットしない。

## D-002 作業ブランチは `claude/puzzle-escape-game-ltbcda`
2026-09-01。STAGING の CLAUDE.md は「作業は main で行う」と定めているが、
このセッションはハーネス側で上記ブランチに固定されている。競合するため、
指定ブランチへ push し、main への統合はユーザーの指示を待つ。

## D-003 `GameState.flags` に `hiddenTextSeen` を追加
2026-09-01。仕様書 05 の GameState には無いフラグ。11_ACCEPTANCE_TEST の
「Flashlight なしで P2 突破不可」を実装として保証するため、壁面文字を実際に
懐中電灯で照らして確認したかを記録し、PC ログインの前提条件にした。
答え (`ORION`) は変更していない。

## D-004 SMALL KEY の用途は壁パネル横キーパッドのカバー解除
2026-09-01。仕様書は金庫から SMALL KEY が出ることだけを書き、使い道を定義して
いない。P4 のキーパッドを金属カバーで塞ぎ、SMALL KEY 所持を挑戦の前提条件に
することで、宙に浮いたアイテムをなくした。

## D-005 隠し部屋は本棚の裏（西側）に置く
2026-09-01。仕様書 03 の上面図では隠し通路が南だが、P5 の成功条件は
「本棚が横へ移動して隠し通路が開く」であり、本棚は上面図では西側にある。
本棚を通路の前に置く方が整合するため、隠し部屋を西 (x -10〜-6) に配置した。
Puzzle の答え・進行順序は変更していない。

## D-006 P6 は本物のアナモルフィック配置で実装する
2026-09-01。仕様書は「完全な錯視モデルが難しければ規定 Camera 範囲での見せ方でよい」
と逃げ道を用意しているが、観測点からの射影で板を配置すれば実装は数式 1 本で足りる
ため、本物の錯視にした。立ち位置がずれると崩れることをテストで担保している。

## D-007 P6 の背景として東側の天井と東壁上端を面光源にする
2026-09-01。黒い板を影絵として読ませるには背後に明るい面が必要。観察窓から
見上げる仰角 (4〜12 度) に入るのは「東側の天井」と「東壁の上端」だけなので、
その 2 面のみ fog を切った面光源にした。東壁全体を光らせる案は室内の暗い雰囲気を
壊すため採らなかった。

## D-008 RESET / タイトルへ戻る / もう一度遊ぶ は保存を消して reload する
2026-09-01。3D シーンを初期状態へ戻す経路を二重に持つと、開いた引き出しや
移動した本棚の取り消し漏れが必ず起きる。`location.reload()` にすれば復元経路は
「セーブから組み立てる」1 本だけになる。

## D-009 エンディングへの遷移は実時間 (setTimeout) で待つ
2026-09-01。演出タイマーは通常フレーム時間ベース (Animator) にしてポーズと
同期させているが、描画が重い環境では 1.6 秒がいつまでも経過せずクリア画面が
出なかった。エンディング遷移だけ実時間に切り替えた。

## D-010 外部アセットを持たない
2026-09-01。テクスチャは Canvas 2D で生成し、効果音・環境音は Web Audio で
合成する。GLB や音声ファイルを置かないことで、読み込み待ち・404・容量の問題を
最初から消した。仕様書 Phase 7 の GLB 差し替えは将来の作業として残す。

## D-011 スロット番号はプレイヤー視点で左から 1→4
2026-09-01。南壁を向くと東 (x が大きい方) が画面左になるため、SLOT 1 を最も
東に置いた。Memo B の「上から順に」との対応が読み取りやすい。

## D-012 ダークな美術方向 + `color-scheme: only light`
2026-09-01。common.md の「ダークテーマは作らない」はサイトのテーマ切替の話と
解釈し、ゲームの美術としての暗い研究室は意図的な固定デザインとして維持する。
その上で UA の自動ダーク化を防ぐため `only light` を宣言し、html/body に背景色と
文字色を明示している（テーマ切替 UI は作らない）。

## D-013 `window.__escape404` に E2E 用ハンドルを公開する
2026-09-01。仕様書 08 が「答えが JS bundle から見えることは許容」としているため
隠す意味がない。ハンドルは UI と同じ経路 (PuzzleManager → Progression) を呼ぶ
だけで、判定を迂回する近道は作らない。

## D-014 Playwright は Chromium の実行パスを探索する
2026-09-01。実行環境に導入済みの Chromium とバージョンが一致しないため、
`PLAYWRIGHT_CHROMIUM_PATH` か `/opt/pw-browsers/chromium` を探して使う。
どちらも無い環境では Playwright 既定のブラウザにフォールバックする。

## D-015 実機 (PC Chrome) 前提で描画を作り直す
2026-09-01。当初はグレイボックス優先で組んだが、対象環境が PC Chrome と
確定したため、描画を実機相応に作り直した。採用したもの:
ACES フィルミックトーンマッピング、MSAA 4x、環境マップ (PMREM + RoomEnvironment)
による間接光と映り込み、UnrealBloom、GTAO (環境遮蔽)、Vignette、
面光源 (RectAreaLight) による天井埋め込み灯、影付き SpotLight 1 灯、埃の粒。
D-010 (外部アセットを持たない) は維持する。

## D-016 マテリアルは手続き生成の PBR マップで作る
2026-09-01。albedo / normal / roughness を Canvas 2D から生成し
(`src/scene/pbr.ts`)、高さマップから Sobel で法線を求める。
床の目地・塗装のゆず肌・ヘアライン仕上げ・ルーバーが実際に凹凸として陰影を持つ。
画像ファイルを持たないので読み込み待ちも 404 も起きない。

## D-017 什器の造形を furniture.ts へ分離する
2026-09-01。Environment.ts が 1000 行を超えたため、
「躯体・設備」= Environment.ts、「什器の造形」= furniture.ts、
「ジオメトリの生成と破棄」= MeshFactory.ts に分けた。
furniture.ts の各関数は BuildContext (factory / materials / register / occlude)
だけを受け取り、進行状態には触らない。

## D-018 Raycast は再帰 + 遮蔽判定にする
2026-09-01。次の 2 つの不具合を修正した。
(1) 操作対象を Group で登録した場合 (引き出しなど) `intersectObjects(targets, false)`
では当たらず、E で操作できなかった。→ 再帰で判定し、ヒットしたメッシュから
祖先方向へ id を辿る。
(2) 操作対象だけを Raycast していたため、壁や什器の向こう側の物を調べられた。
→ 大物を occluders として登録し、手前に遮蔽物があれば操作させない。
E2E に「視線を合わせて E」を通すテストを追加した (この 2 件は UI を直接開く
テストしか無かったために見逃していた)。

## D-019 本棚の本の寸法を固定表にする
2026-09-01。乱数で並べると P4 のヒント本の位置が毎回変わり、
「その本を見て E」の操作テストが不安定になるため固定表から取る。

## D-020 ソフトウェア描画では重いパスを自動で外す
2026-09-01。SwiftShader / llvmpipe を検出したら GTAO・Bloom・影・MSAA を外し、
pixelRatio を 1 に落とす。実機の弱い GPU への保険でもある。
`?gfx=high` / `?gfx=low` で上書きできる (スクリーンショット用の E2E は high を指定)。
Puzzle の判定・進行には影響しない。

## D-021 専用リポジトリ `ohtakayuji/escape404` へ移植し、Cloudflare Pages で配信する
2026-09-01。`ohtakayuji/staging` は本番デプロイをしない下書き場なので、
STAGING の CLAUDE.md の方針どおり専用リポジトリへ移した。
paddlejam と同じ「1 企画 = 1 リポジトリ」構成で、可視性も private に揃えた。

paddlejam は「リポジトリのルートをそのまま配信ルートにする」静的構成だが、
本企画は Vite のビルドが必要なため、リポジトリのルートをプロジェクトルートとし、
配信ルートは Pages のビルド成果物 `dist` とする。この点だけ paddlejam と異なる。

Pages のビルド設定（一次情報: https://developers.cloudflare.com/pages/get-started/git-integration/ ）:
- Framework preset: Vite / Build command: `npm run build` / Build output directory: `dist`
- Production branch: `main`
- Node バージョンは `.node-version` (22) で固定。ビルドイメージ v3 の既定は 22.16.0
  （一次情報: https://developers.cloudflare.com/pages/configuration/build-image/ ）

配信ルートに出す必要がある `robots.txt` は `public/robots.txt` に置いた
（Vite が `dist` 直下へコピーする）。HTML 側の noindex meta は元から入っている。
