## 2026-09-01 視点操作 (Pointer Lock) の開始を作り直した
- 症状: 起動直後に部屋に入ると Windows のマウスカーソルが残り、視点が動かない
- 原因: ロックの要求がキャンバスのクリック待ちだけで、案内は 2.5 秒で消える
  トーストだった。イントロは 6.2 秒で自動終了するため、無操作だと案内が消えた
  状態で放置される
- 修正
  - `src/ui/LookPrompt.ts` を追加（ロック未取得の間だけ出る常設の案内。全画面の
    `<button>` なのでクリックでも Enter / Space でも開始できる）
  - `GameApp` にロック要求と案内表示の判断を集約（`canLook()` / `tryPointerLock()` /
    `syncLookPrompt()`）。イントロのスキップ直後・イントロ終了時・CONTINUE 直後・
    モーダルを閉じた直後・画面クリックで要求する
  - `InputManager.requestPointerLock()` が取得できたかを返すようにした
    （Chrome 111+ の Promise、旧仕様はイベント待ち）
  - イントロを画面クリックでもスキップできるようにした（スキップの二重発火も防止）
  - 中断メニューの注記を「ゲームに戻ると視点操作も再開する」に修正
  - 取得実績があるときの `pointerlockerror` では警告トーストを出さない
    （Chrome は Esc 解除の直後しばらく再取得を拒むため、環境非対応と誤解させない）
- 併発していた不具合も修正: `UIManager.closeModal()` が「閉じた」通知を二重に
  出しており、ロック要求が重なって取得直後に外れ、中断メニューが勝手に開いていた
  （通知は `ModalHost` の `onClose` 経由に一本化）
- テスト追加: `e2e/pointerlock.spec.ts` 5 件（イントロ後・イントロ全視聴後・
  画面クリックでのスキップ・案内クリックでロック取得とカーソル消滅・
  モーダル開閉をまたいだ復帰）
- 実行結果: Vitest 49 件パス / Playwright 18 件パス
